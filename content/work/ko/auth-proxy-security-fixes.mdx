## 무엇을 만들었나

여러 AI 엔진이 브랜드를 얼마나 노출·추천하는지 측정해 리더보드로 보여주는 신규 서비스를 혼자 만들었다. 기존 제품에서 설정·디자인 토큰·공용 UI 프리미티브만 골라 새 저장소로 옮기고, 결제·구독·콘텐츠 같은 기능 결합 모듈은 제외한 뒤 리더보드 도메인으로 다시 구성했다.

인증은 새로 설계하지 않고 기존 제품의 패턴을 이식했다. 토큰을 `HttpOnly` 쿠키로만 다루고 모든 백엔드 호출을 서버 라우트가 중계하는 구조다. 브라우저 JavaScript가 토큰에 접근할 수 없으므로 XSS로 토큰이 새지 않는다.

**이 글은 그 이식 과정에서 무엇을 발견했고, 발견한 것을 어떻게 처리했는지에 대한 기록이다.**

## 이미 프로덕션에서 도는 코드를 옮기는데 왜 검토가 필요한가

이식은 복사가 아니라 **환경이 바뀌는 이동**이기 때문이다.

원본 저장소에서 안전했던 코드가 새 저장소에서도 안전하다는 보장은 없다. 환경변수 이름이 같아도 주입되는 값이 다르고, 배포 파이프라인이 다르고, 프레임워크 버전이 다르다. "이미 돌고 있는 코드"라는 사실은 **그 환경에서 돌고 있다**는 뜻이지 코드가 검증됐다는 뜻이 아니다.

이식 과정에서 4건을 발견했다.

## 발견한 보안 결함 4종

### 1) 클라이언트 번들용 환경변수가 서버의 TLS 검증을 끌 수 있었다

`NEXT_PUBLIC_` 접두사가 붙은 환경변수는 **클라이언트 번들에 그대로 박히는 값**이다. 값이 공개된다는 뜻이고, 빌드 시점에 무엇이 주입되는지가 배포 설정에 달려 있다는 뜻이기도 하다.

그 값이 서버 측 TLS 인증서 검증을 비활성화하는 분기에 연결돼 있었다. 개발 편의로 넣은 우회로가 프로덕션 빌드에서도 켜질 수 있는 경로로 남아 있었다.

### 2) 목업 플래그만으로 프로덕션 인증 우회가 켜질 수 있었다

로컬 개발에서 백엔드 없이 화면을 돌리려고 만든 목업 모드가, **프로덕션 빌드에서도 인증을 건너뛰는 분기**와 같은 플래그를 공유하고 있었다. 플래그 하나가 잘못 주입되면 인증이 통째로 사라진다.

### 3) AI 답변의 출처 URL을 검증 없이 앵커로 렌더했다

제품 특성상 AI가 생성한 답변과 그 답변이 인용한 출처 URL을 화면에 보여준다. **출처 URL은 외부에서 들어온 문자열이다.** 그것을 `<a href>` 에 그대로 넣고 있었다.

`javascript:` 스킴이 들어오면 클릭 시 스크립트가 실행된다. 토큰이 `HttpOnly` 쿠키라 토큰 자체는 못 훔치지만, 사용자 세션으로 임의 요청을 보낼 수 있다.

### 4) 로그인 후 이동할 경로를 검증하지 않았다

로그인 페이지가 `?redirect=` 쿼리를 받아 로그인 성공 후 그 경로로 보내는데, 값이 내부 경로인지 확인하지 않았다. 외부 도메인을 넣으면 **우리 로그인 페이지를 거쳐 공격자 사이트로 보내는 링크**를 만들 수 있다. 피싱에 그대로 쓰인다.

## 이식만 한 것이 아니라 원본의 버그도 고쳤다

원본 구현이 여러 개의 `Set-Cookie` 헤더를 하나의 문자열로 합쳐 다루고 있었다. 쿠키 값에 콤마가 들어가면 경계가 깨진다.

`getSetCookie()` 로 헤더를 배열 그대로 유지하도록 바꿨다. 이식하면서 원본보다 나아진 부분이다.

## 왜 수정 2건을 되돌렸나

1번과 2번의 수정이 **dev 배포 전체를 500으로 죽였기 때문이다.**

두 수정 모두 `NODE_ENV === "production"` 을 기준으로 위험한 분기를 차단하도록 만들었다. 이 판단은 "dev 환경은 `NODE_ENV=development` 로 돈다"는 전제에 기대고 있었다.

그 전제가 틀렸다. **실제 배포는 Docker 컨테이너에서 dev·prod 모두 `NODE_ENV=production` 으로 구동된다.** Next.js 프로덕션 빌드를 실행하므로 자연스러운 설정이다.

되돌리기 전에 확인한 것은 하나다 — **원래 막으려던 위험이 이 환경에서 실재하는가.**

프로덕션 백엔드는 클러스터 내부에서 평문 HTTP로 통신한다. TLS 검증을 끄고 말고 할 대상 자체가 없다. 즉 1번이 막으려던 위험은 이 배포 구조에서 실질적으로 존재하지 않았다.

그래서 두 건을 원복하고, **서버 전용 플래그를 클라이언트 노출 변수와 분리하는 작업**을 후속 과제로 남겼다. 3번과 4번은 환경과 무관한 결함이므로 그대로 유지했다.

되돌린 것은 "보안 수정을 포기한 것"이 아니라 **잘못된 기준으로 만든 수정을 철회한 것**이다. `NODE_ENV` 는 이 문제의 올바른 기준이 아니었다.

## 회전 정책이 도입되면 생길 문제를 미리 막았다

백엔드가 refreshToken 회전 정책(갱신 시 이전 토큰 폐기 + 재사용 감지)으로 갈 예정이었다. 그 정책이 켜지는 순간 터질 구조적 문제가 있었다.

한 화면이 병렬로 던지는 쿼리가 7개다. 세션이 만료된 시점에 이 7개가 **동시에** 토큰 갱신을 요청한다. 회전 정책에서는 1건만 성공하고 나머지 6건은 이미 폐기된 토큰을 재사용하게 된다. 재사용 감지가 작동하면 **토큰 패밀리 전체가 무효화되어 사용자가 강제 로그아웃된다.**

`Map<refreshToken, Promise>` 단일 비행 락으로 동시 갱신을 1회로 합쳤다. 설계에서 신경 쓴 지점이 셋 있다.

- **락의 키를 전역이 아니라 refreshToken 값으로 뒀다.** 전역 키를 쓰면 서로 다른 사용자의 갱신 요청이 같은 Promise를 기다리게 되고, 한 사용자가 다른 사용자의 새 토큰을 받아간다.
- **갱신 요청에 `AbortSignal.timeout()` 을 걸었다.** 기본 대기가 300초인데 락과 겹치면 프로세스가 그만큼 멈춘다.
- **갱신 결과를 성공 / 명시적 거부 / 일시 오류 3상태로 나눴다.** 네트워크 오류를 "인증 실패"로 처리하면 일시적 장애에 사용자가 로그아웃된다. 반대로 명시적 거부를 무시하면 무한 재시도에 빠진다. 판정이 불확실할 때는 fail-closed 로 처리했다.

## 결과

| 항목 | 내용 |
|---|---|
| 발견·수정한 보안 결함 | 4종 (TLS 검증 우회 · 인증 우회 · `javascript:` 스킴 XSS · 오픈 리다이렉트) |
| 유지한 수정 | 2종 (XSS, 오픈 리다이렉트 — 환경과 무관한 결함) |
| 원복한 수정 | 2종 (근거 확인 후. 후속 과제로 기록) |
| 프록시 헬퍼 테스트 | 24케이스, 커버리지 100% |
| 전체 테스트 | Vitest 56개 스위트 + Playwright E2E 1개 |

데이터 레이어도 함께 손봤다. 뮤테이션 자동 재시도를 1에서 0으로 바꿔 **비멱등 POST가 타임아웃 시 중복 생성되는 위험**을 없앴고, 로그아웃 시 인증 스토어만 비우던 것을 프로젝트 스토어·쿼리 캐시·앱 소유 `sessionStorage` 까지 정리하도록 고쳐 계정 간 상태 누수를 막았다.

Sentry를 붙일 때는 프록시가 헤더로 변환한 `Cookie` 와 `Authorization` 이 이벤트에 실려 나가는 것을 전송 전 훅에서 제거했다. **관측 도구가 자격증명 유출 경로가 되지 않게 하는 것이 관측을 붙이는 작업의 일부다.**

## 되돌아보면

**`NODE_ENV` 를 보안 분기의 기준으로 삼은 것이 실수였다.** 이 값은 "빌드가 최적화되었는가"를 말하지 "이 배포가 프로덕션인가"를 말하지 않는다. 두 의미가 대개 일치하기 때문에 착각하기 쉽고, 컨테이너 배포에서는 어긋난다.

수정을 만들기 전에 배포 파이프라인을 읽었어야 했다. 코드만 보고 판단할 수 있는 문제가 아니었다.

다만 되돌리는 과정에서 한 가지는 지켰다고 생각한다 — **"일단 되돌리고 보자"로 처리하지 않고, 원래 막으려던 위험이 이 환경에서 실재하는지 먼저 확인했다.** 확인 결과 실재하지 않았기 때문에 되돌린 것이고, 실재했다면 다른 기준을 찾아 수정을 유지했을 것이다.

서버 전용 플래그를 클라이언트 노출 변수와 분리하는 일은 후속 과제로 남겼다.
