# 글쓰기 가이드

- 작성일: 2026-08-17
- 대상: 글을 쓰는 사람, 그리고 **`blog-publisher` 를 통해 초안을 만드는 AI**

> **함께 볼 문서:** 이 문서는 **어떻게 쓸 것인가**(문체·구조)를 다룬다.
> **무엇을 채우면 화면이 어떻게 되는가**(frontmatter ↔ UI, 복붙 템플릿)는
> [`POST-TEMPLATE.md`](./POST-TEMPLATE.md) 에 있다.

> **이 문서가 이 프로젝트의 핵심 산출물이다.**
> 사이트맵·JSON-LD·llms.txt를 완벽하게 갖춰도, 글이 결론을 앞에 두지 않고 버전을 명시하지 않고 출처를 인용하지 않으면 검색에도 AI 답변에도 인용되지 않는다. 기술 표면은 필요조건일 뿐이고, **실제로 일하는 것은 글의 구조다.**

---

## 0. 대전제: 이 글은 처음부터 끝까지 읽히지 않는다

주 독자는 두 부류다.

1. **에러 메시지를 검색해 온 개발자** — 답만 찾고 나간다. 스크롤하며 스캔한다.
2. **AI 어시스턴트** — 사용자 질문에 답하려고 이 페이지에서 **인용 가능한 조각**을 찾는다.

둘 다 "도입부부터 순서대로 읽는 독자"가 아니다. 따라서 글은 **어느 지점을 잘라내도 그 조각만으로 말이 되게** 써야 한다.

이 하나의 원칙에서 아래 규칙 대부분이 따라 나온다.

---

## 1. 핵심 7규칙

### 1) 결론을 먼저 쓴다 (answer-first)

**모든 섹션의 첫 문장이 그 섹션의 답이다.** 배경 설명 → 과정 → 결론 순서로 쓰지 않는다. 결론 → 근거 → 세부 순서로 쓴다.

```md
❌ ## 왜 hydration mismatch가 나는가
   이 문제를 이해하려면 먼저 React의 렌더링 과정을 알아야 한다. React는...
   (5문단 뒤에야 원인 등장)

✅ ## 왜 hydration mismatch가 나는가
   서버와 클라이언트가 서로 다른 HTML을 만들어냈기 때문이다. 원인의 90%는
   `Date`, `Math.random`, 로케일 포맷, 브라우저 전용 API 네 가지 중 하나다.
   각각이 어떻게 발생하는지 순서대로 본다.
```

AI가 인용할 때 집어가는 것은 대개 **섹션의 첫 문장**이다. 거기에 답이 없으면 그 섹션은 인용되지 않는다.

### 2) 헤딩을 질문형으로 쓴다

독자가 실제로 검색창이나 ChatGPT에 입력할 문장을 헤딩으로 만든다.

```md
❌ ## 원인 분석        ❌ ## 배경         ❌ ## 해결 방법
✅ ## 왜 이 에러가 나는가                  
✅ ## Next.js 16에서 middleware.ts가 동작하지 않는 이유
✅ ## suppressHydrationWarning은 언제 써도 되는가
```

`## 원인 분석` 같은 헤딩은 어떤 검색어와도 매칭되지 않는다. 목차로서는 멀쩡해 보이지만 검색·인용 관점에서는 빈 칸이다.

### 3) 문단은 독립적으로 읽혀야 한다

**"앞서 말했듯이", "위에서 본 것처럼", "이 방법은" 같은 앞 문맥 의존 표현을 쓰지 않는다.** 조각으로 잘려 인용됐을 때 의미가 무너진다.

```md
❌ 이 방법은 앞서 언급한 문제를 해결한다.
✅ `useEffect` 안에서 날짜를 포맷하면 hydration mismatch가 해결된다.
```

지시대명사("이것", "그것")도 최소화하고 대상을 다시 명명한다. 중복이 좀 생겨도 괜찮다 — 스캔하는 독자와 인용하는 AI에게는 그 중복이 도움이다.

### 4) 버전·날짜·환경을 명시한다

"최신 버전에서는" 은 6개월 뒤 거짓이 된다. **구체적인 값을 쓴다.**

```md
❌ 최신 Next.js에서는 이 옵션이 기본값이다.
✅ Next.js 16.2 기준으로 Turbopack이 `next build` 의 기본 번들러다 (2026-08 확인).
```

트러블슈팅 글에는 **환경 블록을 반드시** 넣는다.

```md
| 항목 | 버전 |
|---|---|
| Next.js | 16.2.7 |
| React | 19.2.0 |
| Node | 24.11.0 |
| 확인일 | 2026-08-17 |
```

이건 SEO/GEO 때문만이 아니다. 버전 없는 트러블슈팅 글은 **읽는 사람에게도 쓸모가 없다.**

### 5) 에러 메시지는 전문을 그대로 옮긴다

독자가 검색하는 문자열이 바로 그것이다. 요약하거나 다듬지 않는다.

````md
✅ ```
   Error: Hydration failed because the server rendered HTML didn't match the client.
     at throwOnHydrationMismatch (react-dom-client.development.js:4521)
   ```
````

경로에 포함된 개인 정보(홈 디렉터리 이름 등)만 마스킹한다.

### 6) 1차 출처를 이름과 함께 인용한다

공식 문서, GitHub 이슈, RFC, 체인지로그를 **출처 이름과 날짜를 밝혀** 링크한다.

```md
❌ 알려진 이슈다.
✅ React 19.2 릴리스 노트가 이 동작 변경을 명시한다 ([React Blog, 2026-03](https://...)).
```

근거를 붙인 서술이 인용될 확률이 높다는 것은 GEO 연구의 일관된 방향이다. (구체적 %는 1차 출처로 확인하지 못했으므로 인용하지 않는다 — 이 규칙 자체를 우리도 지킨다.)

### 7) 헤지 표현을 제거한다

확인한 것은 단정하고, 확인하지 못한 것은 **모른다고 명시**한다. 어중간한 완충 표현이 최악이다.

```md
❌ 이 설정이 도움이 될 수도 있습니다. 아마 캐시 문제일 것 같습니다.
✅ `revalidate: 0` 을 설정하면 이 문제가 해결된다. 로컬(Node 24.11)에서 재현·확인했다.
✅ 프로덕션 환경에서도 동일한지는 확인하지 못했다.
```

**"확인하지 못했다"는 헤지가 아니라 정보다.** 숨기지 말고 쓴다.

## 2. 글 구조 템플릿

### 2-1. `troubleshooting` (주력 유형)

```md
---
title: "<에러 메시지나 증상이 그대로 들어간 제목>"
description: "<50자 이상. 무슨 증상을, 왜 생기고, 어떻게 고치는지 한 문장>"
summary: "<2~4문장 TL;DR. 이것만 읽어도 답이 되게>"
category: "troubleshooting"
---

## TL;DR
(summary가 자동 렌더되므로 본문에 중복 작성하지 않는다)

## 증상
무엇이 어떻게 잘못되는가. 에러 메시지 전문을 코드블록으로.

## 재현 환경
| 항목 | 버전 |
(버전 표 — 필수)

## 재현 방법
최소 재현 코드. 실제로 돌아가는 것.

## 원인
왜 이런 일이 생기는가. **첫 문장에 원인을 바로 쓴다.**
근거가 되는 공식 문서/이슈 링크.

## 해결
동작하는 코드. 여러 방법이 있으면 표로 트레이드오프 비교.

## 왜 이 해결이 맞는가
증상만 덮는 게 아님을 설명. 다른 방법을 택하지 않은 이유.

## 이것도 확인해볼 것
비슷하지만 다른 원인들. 이 글로 해결 안 된 독자를 위한 다음 단서.
```

**`왜 이 해결이 맞는가` 를 빠뜨리지 않는다.** 이 섹션이 "스택오버플로 복붙 글"과 갈리는 지점이고, 인용 가치가 가장 높은 부분이다.

### 2-2. `insight`

```md
## 무엇을 알게 됐나      ← 결론. 첫 문장에 핵심 주장
## 어떤 상황이었나        ← 맥락 (짧게)
## 왜 그런가             ← 근거·메커니즘
## 언제 적용되고 언제 안 되나  ← 경계 조건. 여기가 진짜 가치
## 정리
```

`언제 안 되나` 를 반드시 쓴다. 조건 없는 주장은 신뢰도가 낮고, 경계를 밝힌 글이 인용된다.

### 2-3. `note`

짧아도 된다. 다만 **버전·날짜는 예외 없이** 명시한다.

```md
## 무엇
## 언제 쓰나
## 확인 환경
```

## 3. frontmatter 작성 규칙

전체 스키마는 [`CONTENT-CONTRACT.md`](./CONTENT-CONTRACT.md). 여기서는 **잘 쓰는 법**만.

### `title`

- **에러 메시지나 증상을 그대로 넣는다.** 그게 검색어다.
- 낚시·모호한 제목 금지.

```
❌ "삽질 기록: 어제의 그 버그"
❌ "Next.js 이슈 해결기"
✅ "Next.js 16에서 hydration mismatch가 나는 진짜 이유"
✅ "pnpm에서 ERR_MODULE_NOT_FOUND가 뜰 때: strict 격리와 peer dependency"
```

### `description` (50–300자, 필수)

검색 결과에 그대로 노출된다. **무엇을·왜·어떻게를 한 문장에.** 클릭 유도 문구가 아니라 요약이다.

```
❌ "이 문제로 3시간을 날렸습니다. 같은 문제를 겪는 분들께 도움이 되길."
✅ "서버와 클라이언트의 렌더 결과가 갈리는 대표 원인 4가지와, 각각을 어떻게
    특정하고 고치는지 실제 스택트레이스로 정리한다."
```

### `summary` (TL;DR, 2–4문장)

**GEO 관점에서 가장 중요한 필드.** 본문 최상단에 렌더되고, AI가 요약을 찾을 때 가장 먼저 집어가는 덩어리다.

- `description` 과 **다르게** 쓴다. `description`은 "무엇을 다루는 글인지", `summary`는 **"답이 무엇인지"**.
- 이것만 읽고 나가도 문제가 해결되게 쓴다. 아까워하지 않는다.

```
✅ "hydration mismatch의 90%는 Date/random/locale/브라우저 전용 API 중 하나다.
    React 19는 실패한 DOM 노드를 에러에 직접 찍어주므로, 먼저 콘솔의 diff를 읽고
    원인을 특정한 뒤 useEffect 지연 또는 suppressHydrationWarning으로 좁혀 해결한다."
```

### `tags`

- 소문자 kebab-case, 최대 8개
- **검색될 만한 기술명**을 쓴다: `nextjs`, `react`, `typescript`, `pnpm`, `vercel`
- 감상·분류 태그 금지: `삽질`, `기록`, `daily`

## 4. 본문 작성 규칙

| 규칙 | 내용 |
|---|---|
| H1 금지 | 페이지 제목은 `title` 에서 렌더된다. 본문은 `##` 부터 |
| 헤딩 건너뛰기 금지 | `##` → `####` ❌ |
| 코드블록 언어 태그 필수 | ` ```ts `, 파일명 있으면 ` ```ts title="src/lib/foo.ts" ` |
| 코드는 실제로 돌아가야 함 | 의사코드면 그렇다고 명시 |
| 표를 적극 활용 | 비교·버전·트레이드오프는 산문보다 표. 스캔과 추출 양쪽에 유리 |
| 이미지에 의미를 싣지 않기 | 텍스트로 표현 가능한 것을 스크린샷으로 대체하지 않는다. AI는 이미지를 못 읽고, 접근성도 나쁘다 |
| 이미지 `alt` 필수 | 장식이 아니면 내용을 서술 |
| 문단 3–5문장 | 긴 문단은 스캔을 방해한다 |
| 링크 텍스트는 서술적으로 | "여기", "이 링크" ❌ / "React 19.2 릴리스 노트" ✅ |

### 허용 MDX 컴포넌트

| 컴포넌트 | 용도 | 주의 |
|---|---|---|
| `<Callout type="info\|warn\|danger">` | 주의사항 | **핵심 정보를 여기 넣지 않는다.** 본문에서 잘려나갈 수 있다 |
| `<Figure src alt caption>` | 캡션 있는 이미지 | `alt` 필수 |
| `<Aside>` | 곁가지 설명 | 없어도 글이 성립해야 함 |
| `<Details summary>` | 긴 로그·부록 | **접힌 내용은 인용되기 어렵다.** 중요한 건 펼쳐 둔다 |

## 5. 한국어 / 영어 문체 기준

### 공통

- 능동태. 명확한 주어.
- 한 문장 한 가지 주장.
- 과장·감정 표현 자제 ("충격적인", "완벽한", "혁명적인").

### 한국어

- **평어체(~다)로 통일.** 경어체(~습니다)와 섞지 않는다. 기술 문서로서 밀도가 높고, 문장이 짧아진다.
- 기술 용어는 원어 병기 후 일관되게: "하이드레이션(hydration)" → 이후 "hydration"
- 번역투 지양: "~에 대해서", "~을 가지고 있다", "~되어진다"
- 조사 반복으로 길어진 문장은 끊는다.

### 영어

- 짧은 문장. 능동태.
- 한국어 원문의 직역이 아니라 **영어권 개발자가 검색할 표현**으로 다시 쓴다. 제목과 헤딩은 특히 그렇다.
- 번역이 아니라 재작성으로 접근한다. 슬러그만 공유하면 되고 문장 단위 대응은 필요 없다.

## 6. 발행 전 셀프 체크

- [ ] **각 섹션의 첫 문장이 그 섹션의 답인가**
- [ ] 헤딩이 검색될 문장인가 (`## 원인 분석` 같은 게 없는가)
- [ ] 아무 문단이나 하나 골라 떼어내도 말이 되는가
- [ ] 버전·날짜·환경이 구체적으로 적혔는가
- [ ] 에러 메시지 전문이 코드블록에 있는가
- [ ] 1차 출처를 이름과 함께 링크했는가
- [ ] "~일 것 같다", "~도움이 될 수도" 같은 헤지가 남아있지 않은가
- [ ] 확인 못 한 부분을 "확인하지 못했다"고 명시했는가
- [ ] `summary` 만 읽어도 답이 되는가
- [ ] `description` 이 50자 이상이고 요약인가 (낚시가 아니라)
- [ ] JS를 끄고도 본문이 읽히는가

## 7. AI가 초안을 쓸 때 (blog-publisher 경유)

`blog-publisher` 로 초안을 생성할 때 특히 주의할 것:

1. **없는 사실을 만들지 않는다.** 버전 번호, 에러 메시지, 벤치마크 수치는 **실제로 확인된 것만** 쓴다. 그럴듯한 숫자를 지어내는 것이 이 블로그에 가장 치명적이다.
2. **확인 못 한 것은 "확인하지 못했다"로 남긴다.** 빈칸을 추측으로 채우지 않는다.
3. **출처 링크는 실재하는 URL만.** 그럴듯한 문서 경로를 조합해내지 않는다.
4. 초안은 항상 `draft: true` 로 들어온다. 발행 전 사람이 위 §6 체크리스트를 통과시킨다.
5. 개인 경험 서술("3시간을 날렸다")은 사람이 쓴 것만 남긴다. AI가 겪지 않은 경험을 서술하지 않는다.
