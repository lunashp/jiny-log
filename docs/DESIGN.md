# 디자인 방향 — 지니로그

- 작성일: 2026-08-17
- 방향: **에디토리얼 / 매거진**
- 대상: 이 저장소에서 UI를 만드는 사람/에이전트

---

## 1. 디자인 논지 (thesis)

> **모든 트러블슈팅 글은 "문제 → 해결"이라는 이동이다. 이 사이트의 색과 구조가 그 이동을 표시한다.**

장식으로서의 악센트 컬러를 두지 않는다. 색은 **상태를 뜻한다.** 빨강은 문제, 청록은 해결, 회색은 중립. 이건 디버깅 세계의 기존 언어(error/warn/info/success)를 가져온 것이고, 독자가 이미 아는 코드다.

레이아웃도 마찬가지다. 트러블슈팅 글이 요구하는 것 — 버전, 확인일, 환경 — 을 **본문 옆 좌측 레일에 상설 배치**한다. 장식용 사이드바가 아니라, 이 블로그가 실제로 매번 싣는 정보의 지정석이다.

### 이 방향이 피하려는 것

"에디토리얼"은 자칫 세 가지 기성품 중 하나로 수렴한다. 의식적으로 피한다.

| 흔한 기본값 | 왜 안 쓰는가 |
|---|---|
| 크림색 배경(#F4F1EA) + 고대비 세리프 대제목 + 테라코타 악센트 | 어떤 브리프에도 나오는 답. 주제와 무관 |
| 검정 배경 + 애시드 그린/버밀리언 단일 악센트 | 위와 같음 |
| 헤어라인 괘선 + radius 0 + 신문형 다단 | 밀도만 흉내낸 신문 코스프레. 긴 코드블록과 상극 |

**대신:** 차가운 계열의 밝은 지면, **산세리프 대제목**(세리프 대제목의 반대로 감), **세리프는 답변 블록에만** 국소 투입. 대제목을 세리프로 쓰는 게 기본값이므로 뒤집는다.

## 2. 시그니처: 해답 블록 (The Answer Block)

**이 사이트를 기억하게 만드는 단 하나의 요소.**

모든 글은 `summary`(TL;DR)로 시작한다. 이 블록은:

- 본문보다 **큰 세리프**로 조판된다 (본문은 산세리프)
- 좌측에 **카테고리 색 실선 바**가 붙는다 — 이 글이 무슨 종류인지 색으로 즉시 알림
- 페이지에서 세리프가 등장하는 **유일한 곳**이다

기능과 형태가 일치한다. GEO 관점에서 `summary` 는 AI가 가장 먼저 집어가는 덩어리이고([`SEO-GEO.md`](./SEO-GEO.md) §5-3), 사람 독자에게는 "이것만 읽고 나가도 되는" 지점이다. **가장 중요한 텍스트에 유일한 서체 대비를 쓴다.** 대담함은 여기 한 곳에만 쓰고 나머지는 조용히 간다.

```
┃  hydration mismatch의 90%는 Date/random/locale/브라우저
┃  전용 API 중 하나다. React 19는 실패한 DOM 노드를 에러에
┃  직접 찍어주므로, 먼저 콘솔의 diff를 읽고 원인을 특정한 뒤
┃  useEffect 지연으로 좁혀 해결한다.
▲
└─ 카테고리 색 바 (troubleshooting = signal-problem)
```

## 3. 색 토큰

`oklch` 로 정의한다. 하드코딩된 hex를 컴포넌트에 두지 않는다.

> **★ 명도는 눈대중이 아니라 WCAG 대비 계산으로 정했다.** 초기 값은 눈으로 고른 것이었고
> axe 검사에서 4건이 AA(4.5:1) 미달로 걸렸다 (`ink-faint` 2.77, `signal-note` 3.58,
> `signal-resolved` 4.15, 다크 `ink-faint` 3.47). 아래 표는 보정 후 값이며
> `e2e/a11y.spec.ts` 가 회귀를 막는다. **값을 바꾸면 반드시 테스트를 다시 돌린다.**

### 라이트 (기본)

| 토큰 | 값 | 용도 |
|---|---|---|
| `--color-ground` | `oklch(98.6% 0.002 240)` | 페이지 배경. 미세하게 차가운 흰색 — **크림색 아님** |
| `--color-surface` | `oklch(100% 0 0)` | 카드/코드블록 배경 |
| `--color-ink` | `oklch(21% 0.014 250)` | 본문. 순검정 아닌 청흑 |
| `--color-ink-muted` | `oklch(52% 0.012 250)` | 메타데이터, 캡션 |
| `--color-ink-faint` | `oklch(55% 0.012 250)` | 날짜·태그 등 12px 메타 — **4.56:1** |
| `--color-rule` | `oklch(90% 0.006 250)` | 구분선, 테두리 |
| `--color-signal-problem` | `oklch(55% 0.19 27)` | **문제/에러 상태** — 5.13:1 |
| `--color-signal-resolved` | `oklch(53% 0.11 195)` | **해결/링크** — 4.67:1 |
| `--color-signal-note` | `oklch(56% 0.13 75)` | 주의/보류 — 4.56:1 |

### 다크

배경은 **순검정이 아니라 깊은 청흑**. 코드블록이 지면 위에 뜨는 느낌을 유지한다.

| 토큰 | 값 |
|---|---|
| `--color-ground` | `oklch(17% 0.014 250)` |
| `--color-surface` | `oklch(21% 0.016 250)` |
| `--color-ink` | `oklch(93% 0.006 250)` |
| `--color-ink-muted` | `oklch(68% 0.012 250)` |
| `--color-ink-faint` | `oklch(59% 0.012 250)` — **4.56:1** |
| `--color-rule` | `oklch(31% 0.012 250)` |
| `--color-signal-problem` | `oklch(70% 0.16 27)` |
| `--color-signal-resolved` | `oklch(74% 0.11 195)` |
| `--color-signal-note` | `oklch(78% 0.12 75)` |

라이트/다크 모두 **의도적으로 설계**한다. 다크를 라이트의 색 반전으로 만들지 않는다 — 채도와 명도를 각각 다시 잡는다.

### 카테고리 매핑 (색의 의미)

| `category` | 색 |
|---|---|
| `troubleshooting` | `signal-problem` |
| `insight` | `signal-resolved` |
| `note` | `ink-muted` |
| `retrospective` | `signal-note` |

**규칙: `signal-problem` 은 에러·문제·경고 맥락에서만 쓴다.** 그냥 강조하고 싶어서 빨강을 쓰지 않는다. 이 규칙이 깨지면 색의 의미가 죽고 그냥 장식이 된다.

## 4. 타이포그래피

### 서체 3종 (상한, 초과 금지)

| 역할 | 서체 | 라이선스 | 범위 |
|---|---|---|---|
| **Display + Body + UI** | **Pretendard Variable** | OFL 1.1 | KO + Latin. 사이트의 뼈대 전부 |
| **Answer Block 전용** | **Gowun Batang** (고운바탕) | **OFL 1.1** (Google Fonts) | TL;DR 블록, 풀인용구 **only** |
| **Mono** | **JetBrains Mono** | OFL 1.1 | 코드, 메타 레일, 버전·타임스탬프. 한글은 Pretendard 폴백 |

셋 다 OFL 1.1이라 **self-host·상업적 사용·재배포 모두 가능**하다. 고지는 [`public/fonts/LICENSE.md`](../public/fonts/LICENSE.md) 에 동봉했다. 자형은 수정하지 않고 글자 수만 줄였으므로 원본 폰트명을 유지한다.

**왜 산세리프 대제목인가:** 세리프 대제목 + 산세리프 본문이 에디토리얼의 기본값이다. 뒤집는다. Pretendard를 **극단적으로 크게, 자간을 좁혀(-0.03em), 굵게(700–800)** 조판하면 그 자체로 매거진 헤드라인이 된다. 동시에 ko/en 제목이 같은 서체로 나와 이중 언어 사이트의 통일감이 생긴다 — 스크립트마다 다른 얼굴이 나오는 것보다 낫다.

**왜 세리프를 한 곳에만 쓰는가:** 한글 세리프는 용량이 크다. 사용처를 TL;DR로 한정하면 (1) 성능 부담이 국소화되고, (2) 등장이 희소해서 오히려 인상이 강해지고, (3) 로드 실패 시 Pretendard로 폴백해도 레이아웃이 무너지지 않는다.

### 타입 스케일

```css
--text-meta:    0.75rem;                                        /* mono, 레일 */
--text-caption: 0.8125rem;
--text-body:    clamp(1rem, 0.96rem + 0.2vw, 1.0625rem);
--text-lede:    clamp(1.125rem, 1.05rem + 0.35vw, 1.3125rem);   /* Answer Block */
--text-h3:      clamp(1.125rem, 1.05rem + 0.35vw, 1.3125rem);
--text-h2:      clamp(1.375rem, 1.2rem + 0.7vw, 1.75rem);
--text-title:   clamp(2rem, 1.3rem + 3.2vw, 4rem);              /* 글 제목 */
--text-display: clamp(2.5rem, 1.2rem + 5.5vw, 6rem);            /* 홈 */
```

### 행간·자간 (한국어 조정 필수)

한국어는 라틴보다 **행간을 넓게, 자간을 좁게** 가야 읽힌다. 로케일별로 다르게 준다.

| | KO | EN |
|---|---|---|
| 본문 `line-height` | `1.85` | `1.7` |
| 본문 `letter-spacing` | `-0.003em` | `0` |
| 제목 `line-height` | `1.28` | `1.12` |
| 제목 `letter-spacing` | `-0.03em` | `-0.025em` |
| 본문 `max-width` (measure) | `33rem` | `36rem` (≈68ch) |
| `word-break` | `keep-all` **필수** | 기본 |

> `word-break: keep-all` 을 빠뜨리면 한국어가 단어 중간에서 잘린다. 한국어 웹 조판에서 가장 흔한 실수다.

## 5. 폰트 — 해결됨 (2026-08-17)

한글 웹폰트 용량이 이 프로젝트의 최대 리스크였다. **콘텐츠 기반 서브셋으로 해결했다.**

### 무엇을 측정했나

| 방식 | 글 본문 1페이지 다운로드 |
|---|---|
| Pretendard 전체 (가변) | 2,009kB |
| KS X 1001 정적 서브셋 (weight 1종) | 261kB × 필요 weight 수 |
| **dynamic subset** (unicode-range 92 슬라이스) | **402kB** — 게다가 페이지마다 다른 슬라이스를 받아 캐시가 안 듣는다 |
| **콘텐츠 기반 서브셋 (채택)** | **178kB** — 한 번 받으면 사이트 전체에서 재사용 |

dynamic subset 이 한글의 표준 해법으로 알려져 있지만, **이 블로그에는 최악이었다.**
한글 음절이 여러 슬라이스에 흩어져 한 페이지가 16개 슬라이스를 요구했고,
페이지를 옮길 때마다 새 슬라이스를 받는다.

### 채택한 구조

| 패밀리 | 크기 | 서브셋 범위 | preload |
|---|---|---|:---:|
| Pretendard Variable (wght 400–800) | 90kB | 사이트 전체 문자 | ✅ |
| Gowun Batang | 68kB | 사이트 전체 문자 | ❌ |
| JetBrains Mono | 19kB | 라틴 + 기호만 | ❌ |
| **합계** | **178kB** | (예산 250kB) | |

- 가변 축을 **400–800 으로 좁혀** 서브셋했다. 전 축(45–920)을 두면 120kB → 90kB 차이가 난다.
- Gowun Batang 은 Answer Block 전용이지만 **사이트 전체 문자셋**으로 서브셋한다.
  summary 문자만 넣으면 새 글의 한 글자가 폴백으로 빠져 문장 중간에 서체가 섞인다 —
  그게 68kB 아끼는 것보다 나쁘다.
- Pretendard 만 preload 한다. 제목이 LCP 요소이고, 셋 다 preload 하면 서브셋의 의미가 사라진다.

### 콘텐츠 기반 서브셋의 약점과 대응

**글이 추가되면 새 글자가 서브셋에 없다.** `blog-publisher` 가 자동으로 글을 올리므로
사람의 기억에 의존할 수 없다. 그래서 두 개를 둔다:

- `pnpm fonts:build` — 콘텐츠에서 문자를 모아 서브셋 생성 (로컬 전용, Python + fontTools 필요)
- `pnpm fonts:check` — 커밋된 매니페스트와 현재 콘텐츠를 비교. **순수 Node 라 CI 에서 돈다**

생성물(woff2)과 매니페스트를 커밋하므로 **Vercel 빌드에 Python 이 필요 없다.**
새 글자가 생기면 CI 가 실패하며 무엇이 빠졌는지 알려준다.

### 폴백 메트릭 정합

스왑 시 CLS 를 없애기 위해 시스템 폰트를 실제 폰트 메트릭에 맞춰 보정한다
(`ascent-override`, `descent-override`). 수치는 서브셋 파일에서 추출했다:

| 폰트 | ascent | descent |
|---|---|---|
| Pretendard | 0.9521 | −0.2412 |
| Gowun Batang | 0.8800 | −0.1200 |
| JetBrains Mono | 1.0200 | −0.3000 |

### 검증 (e2e/fonts.spec.ts)

- [x] 한글 본문이 Pretendard 로 렌더됨
- [x] 세리프가 Answer Block 밖으로 새지 않음
- [x] 총 다운로드 < 250kB (실측 178kB)
- [x] 폰트 스왑으로 인한 CLS < 0.1
- [x] **폰트를 전부 차단해도 레이아웃이 성립**

## 6. 레이아웃

### 리드 이미지 (cover)

**제목 위가 아니라 아래에 둔다.** 이 사이트의 논지는 "산세리프 대제목이 첫 인상"이라,
이미지를 최상단에 두면 타이포그래피 논지가 밀려난다.

```
카테고리 라벨
큰 제목
    ↓
[ 리드 이미지 ]   ← cover. 좌측 카테고리 색 바가 아래 Answer Block 과 이어진다
    ↓
┃ Answer Block (세리프)
    ↓
본문
```

- `width`/`height` 를 **빌드 타임에 실제 파일에서 읽어** 박는다 → 스왑 CLS 0
- 히어로는 LCP 후보라 `loading="eager"` + `fetchpriority="high"`
- 목록에는 넣지 않는다 — 데이트라인 리스트의 밀도를 깨고 카드 그리드처럼 보이기 시작한다

### 글 본문 (데스크톱 ≥1024px)

```
┌──────────────────────────────────────────────────────────────┐
│  jiny log                              ko / EN      ◐        │  ← 얇은 헤더
├──────────────────────────────────────────────────────────────┤
│                                                              │
│            TROUBLESHOOTING                                   │  ← 카테고리 (mono, 카테고리색)

│            mismatch가 나는 진짜 이유                          │
│                                                              │
│  ┌────────┬─────────────────────────────────────┐            │
│  │ 2026-  │ ┃ hydration mismatch의 90%는       │            │
│  │ 08-17  │ ┃ Date/random/locale/브라우저 전용  │            │  ← ★ Answer Block
│  │        │ ┃ API 중 하나다. ...                │            │     세리프 + 카테고리색 바
│  │ upd.   │ └                                   │            │

│  │        │ ## 증상                              │            │
│  │ ─────  │                                     │            │
│  │ next   │ 서버가 만든 HTML과 클라이언트가...    │            │
│  │ 16.2.7 │                                     │            │
│  │ react  │ ```                                  │            │
│  │ 19.2.0 │  Error: Hydration failed because... │            │

```

**트레이스 레일**이 구조적 장치다. 좌측 고정폭 컬럼에 mono로 발행일·수정일·**버전 스탬프**·태그가 들어간다. 장식이 아니라 [`WRITING-GUIDE.md`](./WRITING-GUIDE.md) 가 트러블슈팅 글에 **의무화한 환경 정보**의 지정석이다. 코드 에디터의 라인 넘버 거터에서 온 형태이고, 이 블로그가 매번 싣는 정보라서 존재한다.

- 레일은 `position: sticky` 로 스크롤을 따라간다. 긴 글 중간에서도 "무슨 버전 이야기였지"가 항상 보인다.
- **< 1024px 에서는 레일이 제목 아래 가로 메타 스트립으로 접힌다.** 숨기지 않는다 — 정보가 사라지면 안 된다.
- `01 / 02 / 03` 같은 순번 마커를 쓰지 않는다. 섹션은 시퀀스가 아니다.

### 글 목록 — 카드 그리드 금지

균일한 카드 그리드는 위계가 없어서 템플릿처럼 보인다. **괘선으로 구분된 데이트라인 리스트**를 쓴다.

```
2026 ─────────────────────────────────────────────────────

08.17  TROUBLESHOOTING
       Next.js 16에서 hydration mismatch가 나는 진짜 이유
       서버와 클라이언트의 렌더 결과가 갈리는 원인 4가지와…
       #nextjs #react #ssr                            ko · en
───────────────────────────────────────────────────────────
07.02  INSIGHT
       pnpm strict 격리가 만드는 문제와 그 이유
       …
```

- 날짜가 좌측 정렬 앵커. 연도는 그룹 헤더로 한 번만.
- 카테고리 라벨은 mono + 카테고리색.
- 우측 끝에 번역 존재 여부(`ko · en`)를 표시. 없는 언어는 흐리게.
- 항목 사이는 괘선 하나. 카드도 그림자도 없다.

### 간격 리듬

```css
--space-rail:    clamp(0px, -4rem + 10vw, 8.5rem);   /* 레일 폭 */
--space-flow:    1.5rem;    /* 문단 간 */
--space-section: 3.5rem;    /* H2 위 */
--space-block:   2rem;      /* 코드/그림 위아래 */
```

균일 패딩을 전면에 바르지 않는다. H2 위 여백은 문단 간 여백의 2배 이상이어야 섹션 경계가 읽힌다.

## 7. 상태 (hover / focus / active)

기본 스타일 방치 금지. 전부 명시적으로 설계한다.

| 요소 | 기본 | hover | focus-visible | active |
|---|---|---|---|---|
| 본문 링크 | `signal-resolved`, 밑줄 `1px` `currentColor/40%` | 밑줄 100% 불투명 + `text-underline-offset` 0.2em→0.12em | **2px 아웃라인, offset 3px, `signal-resolved`** | 투명도 0.7 |
| 목록 항목 | — | 행 배경 `surface`, 제목만 `signal-resolved` | 아웃라인이 행 전체 | — |
| 코드 복사 버튼 | 투명, `ink-muted` | `surface` 배경 + `ink` | 아웃라인 | 스케일 0.96 |
| 언어 전환 | `ink-muted` | `ink` | 아웃라인 | — |
| 언어 전환 (번역 없음) | 투명도 0.35, `cursor: not-allowed` | 툴팁 표시 | — | — |

**`:focus-visible` 아웃라인을 절대 제거하지 않는다.** 키보드로 전 페이지를 돌 수 있어야 한다.

## 8. 모션

**절제한다.** 이 사이트의 목적은 답을 빨리 주는 것이지 인상을 남기는 게 아니다.

허용:
- 링크/버튼 색·투명도 전이 `150ms`
- 목차 현재 항목 표시 이동 `200ms`
- 페이지 진입 시 제목+Answer Block **한 번의 짧은 페이드업**(`opacity` + `translateY 8px`, `400ms`, `ease-out-expo`). 그 이상 없음.

금지:
- 스크롤 연동 패럴랙스
- 섹션마다 등장 애니메이션
- `transform`/`opacity`/`clip-path` 외 속성 애니메이션

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

## 9. 코드블록

본문에서 가장 자주 등장하는 요소다. 대충 두면 안 된다.

- 배경 `surface`, 좌측 `2px` 세로선 `rule`
- 파일명이 있으면 상단에 mono 라벨 바
- 라인 하이라이트는 배경 틴트 (`signal-note` 4% 알파)
- diff 표기: `+` 행 `signal-resolved` 틴트, `-` 행 `signal-problem` 틴트 — **색 의미 체계가 여기서도 일관**
- 가로 스크롤은 코드블록 **내부**에서만 (`overflow-x: auto`). 페이지 본문은 절대 가로 스크롤 없음
- 복사 버튼은 hover 시 등장, **키보드 포커스 시에도 등장**
- 하이라이팅은 빌드 타임 Shiki. 런타임 하이라이터 금지
- **테마는 `github-light-high-contrast` / `github-dark-high-contrast`.** 기본 `github-light` 은
  주황 토큰(#e36209)이 흰 배경에서도 3.49:1 로 AA 미달이라 쓸 수 없다
