# PORTFOLIO.md — 케이스 스터디 표면

이 저장소를 **기술 블로그 + 포트폴리오**로 확장하기 위한 설계 문서.
채용 과정에서 이력서와 함께 제출할 단일 URL을 만드는 것이 목적이다.

> 전제: [`CLAUDE.md`](../CLAUDE.md), [`ARCHITECTURE.md`](./ARCHITECTURE.md), [`CONTENT-CONTRACT.md`](./CONTENT-CONTRACT.md) 를 먼저 읽는다.
> 이 문서는 그 규칙들을 **대체하지 않는다.** 충돌하면 `CLAUDE.md` 가 우선한다.

---

## 1. 왜 별도 사이트가 아니라 여기인가

주력 업무(BrandVis SaaS)가 전부 회사 비공개라 **코드도 화면도 공개할 수 없다.**
그래서 포트폴리오는 "코드 보여주기"가 아니라 **"판단 과정 보여주기"** 로 설계한다.

별도 포트폴리오 사이트를 새로 만들지 않는 이유:

1. 이 저장소에 이미 디자인 토큰·i18n·MDX 파이프라인·접근성/시각회귀 테스트·번들 예산 게이트가 있다. 같은 것을 두 번 짓는 셈이 된다.
2. **이 사이트 자체가 증거물이다.** "품질 게이트를 만든다"고 주장하는 사람의 블로그가 실제로 시각회귀·a11y CI를 돌리고 `llms.txt` 를 제공한다. 말과 물건이 일치한다.
3. 케이스 스터디를 기존 콘텐츠 컬렉션으로 얹으면 렌더러·목차·SEO·JSON-LD가 전부 재사용된다. **신규 코드가 거의 들지 않는다.**

## 2. 확정된 결정

| 항목 | 결정 | 비고 |
|---|---|---|
| 도메인 | `*.vercel.app` 로 시작 | 커스텀 도메인은 나중에 교체. `PUBLIC_SITE_URL` 만 바꾸면 된다 |
| 언어 | **ko + en 둘 다** | 케이스 3건 × 2로케일 = 6편 |
| 회사 업무 공개 범위 | 미확인 → **글 설명만** | 확인되면 케이스 스터디로 승격 (§7) |
| 목표 시점 | 1~2개월 | §8 일정 |

## 3. 케이스 스터디 — 서술 틀

대부분의 포트폴리오는 "무엇을 만들었다"를 쓴다. 이 포트폴리오의 차별점은
**"왜 그렇게 했고, 무엇을 안 하기로 했나"** 이므로 틀에 강제한다.

| 섹션 | 내용 | 분량 |
|---|---|---|
| 맥락 | 제품이 무엇이고 내가 무엇을 맡았나 | 3줄 |
| 문제 | 무엇이 잘못돼 있었나 — **특히 "왜 아무도 못 봤나"** | 1~2문단 |
| 판단 | 고른 것과 **버린 것** | 2~3문단 |
| 결과 | 측정값 + 남긴 것(게이트·도구·문서) | 1문단 + 목록 |
| 되돌아보면 | 한계, 다음엔 다르게 할 것 | 1문단 |

### `되돌아보면` 을 필수로 두는 이유

가장 강한 신호가 여기서 나온다. AIBIX의 *"보안 수정이 배포 모델과 충돌해서 근거를 확인하고 2건을 되돌렸다"* 는
실패담처럼 보이지만, **근거를 확인하고 되돌릴 줄 아는 사람**이라는 증거다.
이력서에서는 방어적으로 읽히는 한계 서술이, 케이스 스터디에서는 신뢰 신호가 된다.

### 글쓰기 규칙

[`WRITING-GUIDE.md`](./WRITING-GUIDE.md) 를 그대로 따른다. 케이스 스터디라고 예외를 두지 않는다.
GEO의 실질은 문체와 구조이며, 이 규칙이 이미 그것을 정의하고 있다.

## 4. 케이스 3건

### ① 사람 눈에는 똑같이 보이는 결함을 자동 게이트로 — 회사 소개 사이트 재구축

- **훅** — 텍스트의 약 50%(FAQ는 84%)가 아코디언에 가려, JS를 실행하지 않는 AI 크롤러가 본문 절반을 못 읽고 있었다. 사람 눈에는 똑같이 보여 코드 리뷰로는 영원히 못 잡는 종류의 결함이다.
- **판단** — 조건부 렌더링 대신 항상 DOM에 두고 CSS(`grid-template-rows 0fr↔1fr`)로만 숨기는 규약. 초기 HTML을 실제 HTTP로 받아 센티널 99개의 생존을 확인하는 게이트.
- **결과** — CI 게이트 17종, 명암비 2,485건 측정 → 실패 402건 → 회귀 0건(WCAG AA), 라우트당 이미지 688.6 → 118.8KB.
- **되돌아보면** — 성능 게이트는 로컬 랩 조건 측정이라 필드 데이터가 아니다. 회귀 감지용으로는 충분하지만 실사용자 지표와 혼동하면 안 된다.
- **실물** — 공개된 실제 사이트 링크.

### ② 읽기 전용 원칙을 문서가 아니라 타입으로 강제하기 — Component Explorer

- **훅** — 유닛 테스트 1,090개가 전부 통과하는 상태에서 1,133개 컴포넌트를 전수 조사했더니, 실제로 디자인을 보여주는 것은 75.3%뿐이었다.
- **판단** — `ReadOnlyFs` 인터페이스 하나로 쓰기 메서드를 아예 노출하지 않는다. 렌더 센서스 도구 자체를 커밋해 재현 가능한 게이트로 만든다. 분류기는 결정적 근거가 없으면 `other` 로 남긴다(틀린 분류가 무분류보다 나쁘다).
- **결과** — 렌더 비율 75.3% → 91.8%, 테스트 1,134건 전부 통과, 엔진 구문 커버리지 94.76%, MCP 도구 6종.
- **되돌아보면** — `other` 로 남기는 선택의 트레이드오프. 재현율을 포기하고 정밀도를 샀다.
- **실물** — 공개 저장소 + 코드 링크.

### ③ 에이전트가 글을 발행하게 만들기 — jiny-log + blog-publisher

- **훅** — 이 사이트가 그 결과물이다.
- **판단** — `draft-by-default`, GitHub 커밋 → Vercel 자동배포, 엔진을 MCP 서버로 노출. **Next.js 16으로 구현한 뒤 클라이언트 컴포넌트를 전부 제거해도 JS 138KB가 남는 것을 실측하고 Astro로 옮겼다(현재 2.2KB).** 경위는 [`ARCHITECTURE.md`](./ARCHITECTURE.md) §1.
- **결과** — 번들 예산 하드 게이트, JS 0바이트 기본 원칙, 접근성·시각회귀 CI.
- **되돌아보면** — 프레임워크를 갈아엎는 판단의 비용과, 되돌릴 조건을 먼저 적어둔 것의 값어치.
- **실물** — **지금 보고 있는 화면.**

③은 "측정하고 판단한다"는 주장의 가장 싼 증거다. 이미 저장소에 경위가 문서로 남아 있어 새로 만들 근거가 없다.

## 5. 정보 구조

```
/{locale}                 홈 — 한 문장 소개 + 케이스 3건 + 최근 글        ← 개편
/{locale}/work            케이스 목록                                    ← 신규
/{locale}/work/{slug}     케이스 상세                                    ← 신규
/{locale}/about           소개 · 이력 요약 · 이력서 PDF                   ← 신규
/{locale}/posts …         글 (기존 그대로)
/{locale}/tags/{tag}      (기존 그대로)
```

### 홈을 바꾸는 이유

현재 홈은 `태그라인 + 설명 + 글 목록` 이다. 채용자가 처음 보는 화면이 글 3편이면 약하다.
케이스 3건을 전면에 두고 글 목록은 그 아래로 내린다.

### 표현 규칙 (중요)

`CLAUDE.md` 의 **"카드 그리드 인덱스 금지"** 가 여기에도 적용된다.
케이스 목록도 **에디토리얼 데이트라인 리스트**로 만든다. 카드 3장을 나란히 놓지 않는다.
`DESIGN.md` 체크리스트의 *"기본 Tailwind 템플릿처럼 보이는가?"* 가 실패 신호다.

## 6. 구현 계약

### 6-1. 콘텐츠 컬렉션 추가

```
content/work/{ko,en}/<slug>.mdx
```

- 슬러그는 **ASCII**, 날짜 프리픽스 금지 (`CLAUDE.md` 규칙).
- `src/content.config.ts` 에 `work` 컬렉션과 `WorkFrontmatterSchema` 를 추가한다. `retainBody: true` 유지.
- 프론트매터는 글 스키마를 상속하되 케이스 전용 필드를 더한다: `role`, `period`, `stack[]`, `links[]`(라벨 + URL), `summary`.
- **스키마 검증 실패는 빌드 실패다** (규칙 8). 경고로 낮추지 않는다.

### 6-2. 격리 레이어를 반드시 경유한다

`astro:content` 직접 import 금지(규칙 1, eslint 로 강제)는 케이스 스터디에도 동일하다.
`src/lib/content/` 에 `getWorks` / `getWorkBySlug` / `renderWork` 와 도메인 타입 `Work` / `WorkSummary` 를 추가하고,
페이지는 `@/lib/content` 만 import 한다.

**draft 필터링은 진입점 한 곳에서 수행한다**(규칙 2). 케이스용 필터를 따로 만들지 않는다 —
따로 만들면 목록·사이트맵·`llms.txt` 중 하나를 언젠가 빠뜨린다.

### 6-3. 새 라우트에 딸려오는 것들

`CLAUDE.md` 작업 지침: *"새 페이지/라우트를 추가하면 사이트맵·hreflang·JSON-LD 반영 여부를 같은 작업 안에서 확인한다."*

- [ ] 사이트맵에 `work` 라우트 포함, draft 제외
- [ ] hreflang — 현재 `getAvailableLocales(slug)` 는 **글 컬렉션 전용**이다(`PostList.astro` 에서 사용). 케이스에 그대로 쓰면 존재하지 않는 글을 조회한다. 컬렉션을 인자로 받도록 일반화하거나 work 전용 함수를 만든다. 번역 없는 로케일은 **404가 정답**이며 리다이렉트하지 않는다
- [ ] JSON-LD — 케이스 상세는 `Article` 이 아니라 `CreativeWork` 가 적절한지 검토
- [ ] OG 이미지 — `src/pages/og/[...slug].ts` 가 work 슬러그를 커버하는지
- [ ] `llms.txt` 에 케이스 스터디 포함 (AI가 인용하기 좋은 형태가 이 저장소의 존재 이유)
- [ ] raw markdown 라우트를 work 에도 제공할지 결정
- [ ] **RSS 에는 케이스를 넣지 않는다** — 구독자가 기대하는 것은 글이다

### 6-4. 예산과 품질 게이트

- 번들 예산은 **하드 게이트**다. `/work` 는 목록 라우트이므로 **JS < 10KB(gzip)**. 예산을 올려서 통과시키지 않는다.
- 프레임워크 아일랜드 금지(규칙 3). 인터랙션이 필요하면 CSS → 순수 DOM `<script>` 순으로 해결한다.
- 애니메이션은 `transform` / `opacity` / `clip-path` 만(규칙 5). `prefers-reduced-motion` 존중.
- 색·간격은 토큰으로만(규칙 6). **새 색 토큰을 추가하면 `pnpm test:e2e` 를 다시 돌린다.**
- 케이스 스터디를 추가한 뒤 `pnpm fonts:check` 를 돌린다. 실패하면 `pnpm fonts:build` 후 `public/fonts/` 와 `tools/fonts/charset.json` 을 함께 커밋한다.

### 6-5. 커밋

`content:` 타입을 쓰고, **코드 변경과 글 변경을 한 커밋에 섞지 않는다.**
라우트 구현(`feat:`)과 케이스 원고(`content:`)는 별도 커밋이다.

## 7. 회사 업무 서술

`/{locale}/about` 하단에 **`그 외 업무`** 섹션으로 둔다. 케이스당 3~4줄, 링크 없음.
분석 대시보드 · 백오피스 · AIBIX · 사내 ITSM 이 대상이다.

공개 범위가 확인되면 케이스 스터디로 승격한다. 그때까지는 **화면 캡처·코드 조각을 올리지 않는다.**


## 9. GitHub 표면 정비 (1주차, ROI 최대)

이력서에 `github.com/lunashp` 를 적어두었으나 **현재 그 링크는 마이너스로 작동한다.**

| 문제 | 조치 |
|---|---|
| Component Explorer가 `frontend-design` 이라는 이름에 설명 0자로 묻혀 있음 | **`component-explorer` 로 이름 변경** + 설명·토픽 작성. GitHub이 리다이렉트하므로 안전 |
| 프로필 README 없음 | `lunashp/lunashp` 신설 — 한 화면에 3개 프로젝트 + 블로그 링크 |
| 항해플러스 과제 저장소 10개(대부분 fork)가 목록을 차지 | **아카이브 처리** — 공개는 유지하되 `보관됨` 표시로 현재 작업과 구분 |
| Pinned 미지정 | `component-explorer` · `jiny-log` · `blog-publisher` 를 포함해 6개 지정 |
| `component-explorer` 최신 작업이 `feat/component-preview-and-scan-fixes` 브랜치에 있음 | 기본 브랜치에 머지되어 있는지 확인. 방문자가 보는 것은 기본 브랜치다 |

## 11. 미결 사항

- **회사 업무 공개 범위** — 확인 필요. 결과에 따라 케이스가 3건에서 4~5건으로 늘 수 있고, 포트폴리오의 무게중심이 개인 프로젝트에서 실무로 옮겨간다. **가장 먼저 확인할 것.**
- 케이스 상세의 JSON-LD 타입(`Article` vs `CreativeWork`) — 구현 시 결정
- work 에 raw markdown 라우트를 제공할지 — AI 인용 관점에서는 제공이 맞으나 비용 확인 필요
- 커스텀 도메인 구입 시점
